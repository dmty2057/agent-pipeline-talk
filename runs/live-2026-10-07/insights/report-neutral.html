Where Things Go Wrong

Most of your friction comes from Claude starting down the wrong path before you redirect it, documents that are too long in early rounds, and long-running servers or builds that stall.

Wrong initial approach that you had to correct
Wrong approach was your most common friction (7 instances). Claude sometimes picked a cautious or indirect route, and you steered it to the obvious one. Stating the preferred method, format and data source up front would cut these detours.
  • Claude tried to reconstruct an API from guesses until you pointed it to the documented endpoint.
  • Claude built an interactive page for a report you wanted as a plain PDF.
Output too long until several rounds of trimming
Documents and UI drafts often arrived with too much text or spacing, so you spent a few rounds cutting them down. Giving a page limit or a reference design early would likely get you there faster.
  • A requirements document needed several trimming rounds before it fit on two pages.
  • Early redesign drafts had extra copy and uneven spacing until an HTML concept was approved.
Fragile long-running processes
Dev servers and long builds occasionally hit tool timeouts, which interrupted otherwise successful sessions. Running them in the background with a health check avoids most of this.
  • A dev server stopped after a tool timeout and had to be restarted in the background.
  • A long build exceeded the command time limit and was rerun as a background task.

On the Horizon

Your work already runs as staged pipelines with review points, so the next step is to let agents iterate on their own against automated checks and bring you in only for judgment calls.

Self-Checking Loops With Critic Agents
A worker agent could produce each output, a separate critic agent could score it against written acceptance criteria, and the loop could repeat until it passes or truly needs a human.
Getting started: Use the Agent tool to spawn one worker per item plus an independent critic, and keep the loop state in a file inside the repo.
Paste into Claude Code:
Set up a review loop: for each item, a worker produces it, a critic scores it against docs/criteria.md, and the worker retries up to 5 times. Keep state in .pipeline/state.json and give me a summary table at the end.
Parallel Stages Built Against Tests
A lead agent could split the remaining stages into specs with failing tests, then parallel agents in separate git worktrees would implement each stage until its tests are green.
Getting started: Use git worktrees so each stage gets its own branch, and run long builds in the background.
Paste into Claude Code:
For each unfinished stage: write a short spec and failing tests, spawn one agent per stage in its own worktree, merge when green, run the full suite, and report stage, tests, status.
